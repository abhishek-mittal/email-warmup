EmailWarm · how it works today

One warmup email, from schedule to WarmupHub

EmailWarm builds sender reputation by having inboxes exchange small amounts of real mail and treat it well: open it, star it, reply, pull it out of spam. Step through the diagram to follow a single message through every part of the system. State as of 3 October 2026, branch feat/mr-warmup-core.

Step 1

Plan the day

The ledger row on the right is the same database row throughout. Every worker writes its result there as it happens, which is what lets a retry pick up where a failed attempt stopped instead of repeating it.

Checked immediately before every send

A slot is reserved hours before it fires, so the send worker checks again at the last moment. If any rule fails, the row is marked canceled and no mail leaves.

  • Sender is active. Paused, errored, pending and graduated inboxes send nothing.
  • Never the same domain. A sender is never paired with a mailbox on its own domain.
  • Consent on both sides. The shared pool needs recorded opt-in from sender and receiver.
  • Receiver is taking part. Active inbox, active membership, not quarantined.
  • Private pool stays private. A pool inbox is only used by the account that owns it.
  • One submission per slot. The claim is a conditional update, so a job delivered twice sends once.
  • No stop switch is on. An operator can halt all sending, one provider, or one account; queued sends obey it.
  • Bounce rate is under 3%. An inbox over the limit is held until an operator reviews it.

How a mailbox gets connected

Three ways in. All of them end the same way: the mailbox is only activated after it has actually signed in over SMTP, and IMAP where it needs to receive.

  1. You choose a providerGmail or Outlook by sign-in, or any server by SMTP and IMAP details. A checkbox decides whether the inbox joins the shared pool.
  2. A single-use ticket is issuedFor Gmail and Outlook the API stores a random, five-minute ticket tied to your account, then sends you to the provider's consent screen.
  3. The provider sends you backThe return address is a mailbox-only page, separate from account login. It works only while you are signed in.
  4. The ticket is checked and burnedEdited, replayed, expired or someone else's tickets are rejected before any token is requested.
  5. Tokens are stored encryptedAES-256-GCM. The mailbox address comes from the provider's identity token, never from the browser.
  6. Pre-check runsSign in over SMTP, sign in over IMAP, create the WarmupHub folder, look up DNS. Pass, and the inbox is active.

Bulk import (CSV or JSON) creates inboxes as pending. A background job runs the same sign-in test, then marks each one active or errored. Reconnecting a mailbox you already have updates it in place and keeps its warmup day.

How your browser talks to the API

1 · browserDashboardCalls /api/backend/… on the same site with your session cookie. Holds no API credential.
2 · web serverNext.js proxyLooks your session up in the store, checks the request came from this site, allows only known paths, signs a 60-second pass.
3 · apiNestJSVerifies the pass, takes your user id from it, and checks you own the inbox you asked about.
4 · storagePostgres and RedisAccounts, inboxes, the send ledger, schedules; job queues for every worker.

Because the signing key never leaves the server, nothing a browser sends can change who the API thinks is calling.
