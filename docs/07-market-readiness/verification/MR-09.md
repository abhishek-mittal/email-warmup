# MR-09: entitlements at every entry point

**Owner:** Claude · **Date:** 2026-10-04 · **Branch:** `feat/mr-warmup-core` (uncommitted) · **Status:** in progress

Billing is deferred (DEMO_MODE; MR-04 not worked), so this cycle targets the
entitlement *enforcement* gaps that do not depend on Stripe.

## Done

- **Atomic inbox-slot reservation (race fix).** The old `count` then `insert`
  pattern let two concurrent connects both pass the check and overrun the cap.
  `BillingService.withReservedInboxSlot(userId, insert)` now runs a
  `db.transaction` that takes a per-user advisory xact lock
  (`pg_advisory_xact_lock(hashtext('inbox:'+userId))`, same key space as
  placement), re-counts inside the lock, and runs the insert on the same
  transaction handle — check and write commit together. Applied to:
  - custom SMTP connect (`InboxService.connectCustomSmtp`),
  - OAuth link completion (`InboxService` link path; a full plan surfaces as the
    typed `MailboxLinkError('limit')`),
  - batch import (`InboxService.batchUpload`): the whole batch reserves under one
    locked transaction, each row insert is a savepoint (nested transaction) so a
    row-level error keeps the T020 partial-success contract; analysis is enqueued
    only after commit.
- **Placement units** were already reserved atomically under
  `pg_advisory_xact_lock('placement:'+userId)` (verified, unchanged).
- **Free/unknown plans rejected by default.** `PLAN_LIMITS[plan]?.inboxes ?? 0`
  and the placement quota default already refuse unknown/free plans (0 slots, no
  placement) rather than granting a trial allowance.

Tests: integration `connect.int-spec.ts` — 5 simultaneous connects on a trial
plan yield exactly 3 inboxes, 2 refused with a `limit` error, DB holds 3.
`mailbox-link.int-spec.ts` — a full plan refuses the link with a typed `limit`
error via the real reservation (no mock). Both specs now use the real
`BillingService`. Backend: tsc clean, 611 unit + 122 integration pass, build clean.
