## Original defect

`frontend/src/lib/api.ts` read `NEXT_PUBLIC_BETTER_AUTH_SECRET` and signed API tokens in the browser. With the variable set, anyone could sign a token for any user id. With it unset, client-side API calls carried no token. The local `frontend/.env.local` has the variable set.

## What changed

- The browser calls same-origin `/api/backend/*`. `lib/server/backend-proxy.ts` validates the session against the session store (cookie cache bypassed), takes the user id from it, signs a 60-second credential on the server and forwards the request.
- Only `inboxes`, `pool-inboxes`, `billing` and the mailbox-link start are reachable, each with a fixed method list. `internal`, `webhooks`, `health` and anything else return 404.
- Mutations need an `Origin` matching the site. Caller-supplied `Authorization`, `Cookie` and other headers are dropped. Bodies are capped at 2 MiB; upstream redirects are not followed.
- `bearer-token.ts` is marked `server-only`. Nothing in client code references the public secret.
- The API rejects tokens claiming more than two hours of validity.

## Evidence

Production build with sentinel values for `BETTER_AUTH_SECRET`, `NEXT_PUBLIC_BETTER_AUTH_SECRET` and `INTERNAL_SECRET`; search of `.next/static`:

| Search | Files |
|---|---|
| Each sentinel value | 0 |
| `NEXT_PUBLIC_BETTER_AUTH_SECRET` | 0 |
| `importKey` or `mintBearerToken` | 0 |

Live checks through the running frontend: no session 401; internal path 404; signed in 200; mutation without Origin 403; foreign Origin 403; forged `Authorization` header ignored (served as the session user).

## Operator actions required

1. Delete the `NEXT_PUBLIC_BETTER_AUTH_SECRET` line from `frontend/.env.local` and from any deployment configuration.
2. If a build with that variable set was ever served to anyone, rotate `BETTER_AUTH_SECRET` on both services and rebuild. Until rotation, a token signed with the old value is still accepted by the API. Whether any such build was deployed was not inspected.
3. Set `API_URL` on the frontend server for the API address. `NEXT_PUBLIC_API_URL` still works as a fallback.

## Not done

- Tenant-isolation HTTP suite across every controller (MR-22). Ownership checks exist per endpoint; they were not swept.
- The API still accepts any correctly signed token without a session lookup; revocation is enforced at the proxy. The API should not be publicly reachable (MR-06 ingress).
- `app.enableCors()` on the API is still open to all origins.
