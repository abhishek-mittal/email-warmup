## Original defect

The start endpoints were public, so the state was `{"userId":"anonymous"}` or an unsigned user id in base64. The public callback decoded it and linked the mailbox to whatever id it named. The redirect URI pointed at the account-login callback owned by better-auth, so the mailbox callback was never reached.

## What changed

- Start requires a signed-in user. State is 32 random bytes; only its SHA-256 is stored, with user, provider, PKCE verifier (encrypted), consent choice and a five-minute expiry.
- The provider returns to `/api/mailbox-oauth/callback/{google,microsoft}` on the frontend, separate from `/api/auth/callback/*`. That route requires a session and forwards to the API as that user.
- The API consumes the state in one conditional update (hash, user, provider, unused, unexpired) before any token exchange. The public API callbacks are removed.
- The mailbox address is read from the ID token returned by the token endpoint. `openid email` is now requested. The Google userinfo call was not covered by the mail scope, and Microsoft Graph `/me` cannot be called with an Outlook-audience token.
- Typed results: `denied`, `state_invalid`, `provider_error`, `duplicate`, `limit`, `connection_failed`. The browser is redirected to a fixed in-app page.
- Linking a mailbox the user already has reconnects it in place and keeps warmup progress.

Override the redirect with `GOOGLE_MAILBOX_REDIRECT_URI` / `MICROSOFT_MAILBOX_REDIRECT_URI`; the default is `APP_URL/api/mailbox-oauth/callback/<provider>`.
